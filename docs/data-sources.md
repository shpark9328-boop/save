# KTX 좌석 데이터 확보 방법 검토

> 결론부터: **"매진/잔여좌석"을 실시간으로 알려주는 공개 API 는 존재하지 않는다.**
> 그래서 이 프로젝트는 좌석 데이터 소스를 인터페이스 뒤로 숨기고, 기본값을 mock provider 로 둔다.

## 1. 공식 경로 조사

| 경로 | 무엇을 주는가 | 좌석(매진/잔여) 제공 | 비고 |
| --- | --- | --- | --- |
| 공공데이터포털 [국토교통부(TAGO) 열차정보](https://www.data.go.kr/data/15098552/openapi.do) | 출발·도착역 기준 열차 운행 시간표, 열차 등급, 운임 | ❌ | `getStrtpntAlocFndTrainInfo` 등. 인증키 발급 필요 |
| 공공데이터포털 [한국철도공사 열차운행정보](https://www.data.go.kr/data/15125762/openapi.do) | 여객열차 운행계획/운행정보(열차번호, 역, 계획 시각) | ❌ | 운행 계획 데이터이지 예약 재고가 아님 |
| [한국철도공사 Open API](https://info.korail.com/info/contents.do?key=761) (승차권 진위확인 등) | 특정 업무용 API | ❌ | 좌석 재고 조회 용도 아님 |
| 코레일 웹/앱 예매 화면 | 좌석 재고 **있음** | ✅ | 단, 공개 API 가 아니라 예매 시스템 내부 인터페이스 |

즉, 공개적으로 합법적으로 받을 수 있는 것은 **시간표/운임**까지이고, "이 열차 일반실이 지금 매진인가"는
코레일 예매 시스템만 알고 있다.

## 2. 비공식 경로를 쓰지 않는 이유

인터넷에는 코레일 모바일 앱의 내부 엔드포인트를 역분석한 라이브러리들이 존재한다. 이 프로젝트는
그 경로를 **구현하지 않는다.** 이유는 다음과 같다.

- **이용약관**: 코레일 이용약관은 자동화된 수단으로 예매 시스템에 반복 접근하는 행위를 제한한다.
  좌석 조회는 예매 시스템의 일부다.
- **로그인 요구**: 해당 인터페이스는 회원 로그인(또는 그에 준하는 세션)을 요구한다.
  서비스 운영자가 사용자 계정 자격증명을 대신 보관·사용하는 구조는 개인정보/보안 측면에서 정당화하기 어렵다.
- **자동화 차단 장치**: 접근 제한·캡차 등 보호 장치가 있을 수 있으며, 이를 우회하는 것은 이 프로젝트의 범위 밖이다.
  (우회 코드는 작성하지 않는다.)
- **부하**: 매크로성 반복 조회는 실제 이용자의 예매를 방해한다.

따라서 코드베이스에는 **스크래퍼가 들어 있지 않다.** 대신 아래 3번의 어댑터 자리를 비워 둔다.

## 3. 이 프로젝트가 택한 구조

```
                 TrainDataProvider (인터페이스)
                          │
   ┌──────────────────────┼───────────────────────────┐
   │                      │                           │
MockTrainProvider   TagoTrainProvider          HttpSeatProvider
(기본값, 데모용)     (공공데이터 시간표,         (좌석 데이터를 적법하게
                     좌석은 UNKNOWN)            보유한 주체의 엔드포인트)
```

- **MockTrainProvider** — 기본값. 결정적 시간표 + 시간 버킷마다 다시 추첨되는 좌석 상태.
  `SOLD_OUT → AVAILABLE → SOLD_OUT` 전이가 실제로 발생하므로 알림 파이프라인 전체를 검증할 수 있다.
- **TagoTrainProvider** — 공공데이터포털 열차정보 API. 실제 열차번호/시각을 가져오지만
  좌석 상태는 전부 `UNKNOWN` 으로 반환한다. 엔진은 `UNKNOWN` 에 대해 **알림을 보내지 않는다.**
  (없는 기능을 있는 것처럼 만들지 않기 위한 의도적 설계다.)
- **HttpSeatProvider** — 좌석 재고 데이터를 적법하게 취득할 수 있는 주체(제휴 API 보유자 등)가
  [docs/providers.md](./providers.md) 의 JSON 계약을 만족하는 엔드포인트를 제공하면,
  환경변수 두 개만 바꿔 그대로 실서비스가 된다.

## 4. 제공처 보호 (실제 연동 시 반드시 지킬 것)

| 항목 | 구현 |
| --- | --- |
| 조회 합치기 | 같은 `(노선, 날짜)` 는 `WatchGroup` 1건으로 묶어 사용자 수와 무관하게 1회만 조회 |
| 재조회 간격 | `GROUP_MIN_INTERVAL_SECONDS` (기본 60초) |
| 요청 간 간격 | `PROVIDER_MIN_GAP_MS` (기본 1.5초) + provider 자체 `minIntervalMs` 중 큰 값 |
| 분당 상한 | `PROVIDER_MAX_RPM` (기본 30) |
| 실패 백오프 | 연속 실패 시 지수 백오프(최대 1시간), 지원하지 않는 구간은 6시간 |
| 불필요한 조회 제거 | 활성 알림이 없는 그룹은 자동 비활성화, 여행일이 지난 알림은 자동 만료 |
| robots.txt | HTML 스크래핑을 하지 않으므로 해당 사항 없음. 스크래핑 어댑터를 붙인다면 반드시 확인할 것 |

## 5. 알아둘 제약

- 좌석 정보를 제공하지 않는 provider(`tago`)로 운영하면 서비스는 "시간표 뷰어"가 된다.
  UI 와 관리자 화면에 그 사실이 경고로 표시된다.
- 폴링 주기가 60초라면 1분 이내에 사라지는 취소표는 놓칠 수 있다. 주기를 줄이는 것은
  제공처와의 합의(요청 허용량) 안에서만 해야 한다.
- 알림은 "좌석이 있었다"는 시점의 사실이다. 사용자가 예매 페이지에 도달했을 때 이미 팔렸을 수 있다.
